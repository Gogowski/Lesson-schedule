# План бесплатного запуска расписания

Проверено 6 октября 2026 года. Условия: 0 ₽, без привязки карты и автоплатежей; владелец редактирует расписание, второй человек только смотрит; оба пользователя находятся в России. ФИО и контакты в расписание не добавляем.

## Выбранная схема

- **Render Static Site** собирает и выдаёт сайт из приватного GitHub-репозитория. GitHub Pages на аккаунте GitHub Free не подходит: репозиторий сейчас приватный, а бесплатный Pages доступен для публичных репозиториев. Делать репозиторий публичным нельзя: в нём есть демо-расписание и ссылки, а история Git сохраняет старые версии.
- **Supabase Free** хранит аккаунты и расписание. RLS ограничивает чтение пользователями из `schedule_access`; запись разрешена только роли `editor`. Публичный signup выключен.
- Браузеру передаётся только publishable key. Secret/service-role key никогда не помещается в клиентский код или переменные `VITE_*`.

Render Static Site раздаёт готовые файлы через CDN, без отдельного запущенного web-service процесса. По документации Render статические сайты бесплатны, но используют общий лимит исходящего трафика и минут сборки. Если лимиты закончатся, сервис может приостановить сайт или новые сборки; без платёжного метода он не сможет автоматически списать деньги. Платные тарифы и дополнения не подключаем.

Supabase Free даёт 500 МБ базы и 5 ГБ исходящего трафика, но может приостановить проект после 7 дней низкой активности. Для двух человек лимитов хватит, однако бесплатная схема не гарантирует доступность в любой момент: приостановленную базу владелец возобновляет вручную в панели. У бесплатного плана нет автоматических резервных копий базы и SLA.

## Почему GitHub Pages заменён на Render

В настройках GitHub явно указано, что репозиторий приватный, а GitHub Pages предлагает обновить план или сделать репозиторий публичным. Согласно документации GitHub, Pages на GitHub Free доступен в публичных репозиториях. Публичность раскрыла бы не только код, но и текущую/прошлую историю репозитория. Render Static Site позволяет раздавать фронтенд из приватного репозитория; единственная внешняя настройка, которую надо ещё подтвердить, — разрешить Render доступ GitHub App только к `Gogowski/Lesson-schedule`.

## Состояние настройки

- Supabase-проект `Lesson schedule` существует на бесплатном плане, регион `eu-west-1`.
- Таблицы и RLS-политики уже существуют; права проверены: анонимный доступ отсутствует, редактор может записывать, читатель сможет только читать.
- Публичная регистрация выключена. В Supabase пока нет пользовательских аккаунтов, строк доступа и сохранённого расписания.
- В GitHub Actions заданы `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` для проверки сборки.
- В репозитории подготовлен `render.yaml`; GitHub Actions проверяет TypeScript и production-сборку. Render ещё не подключён, сайт ещё не опубликован.
- Production-сборка больше не включает локальные демо-уроки, имена и meeting URLs.

## Что осталось сделать

1. Пользователю войти или зарегистрироваться в Render. Принять юридические условия, если они появятся, должен сам пользователь.
2. При подключении GitHub App выбрать только репозиторий `Gogowski/Lesson-schedule`; не разрешать доступ ко всем репозиториям. Затем создать Blueprint из `render.yaml` на бесплатном Static Site и указать publishable key.
3. Скопировать выданный Render URL в Supabase **Authentication → URL Configuration** как Site URL и разрешённый Redirect URL.
4. В Supabase вручную создать два пользователя, задав пароли самостоятельно в dashboard. Не присылать пароли в чат. Встроенная SMTP-служба Supabase Free ограничена: письма не отправляются на произвольные адреса, а текущий лимит около двух писем в час. Поэтому восстановление пароля письмом пока не настроено.
5. Добавить в `schedule_access` UID владельца с ролью `editor`, второго пользователя с ролью `viewer`. Перед этим проверить UID и роли.
6. Сначала проверить вход, чтение и отказ в записи для читателя/анонимного запроса. Только после этого импортировать настоящее расписание без лишних контактов.
7. Сверить сайт из российских сетей обоих пользователей. Запросы к Supabase с компьютера владельца проходят, но сеть второго пользователя и доступность нового Render URL ещё не проверены.
8. После запуска периодически экспортировать JSON-резервную копию из приложения и хранить вне репозитория.

## Проверки этой версии

- `npm run lint` — прошёл.
- `npm run build` с реальными публичными настройками Supabase — прошёл.
- Проверка собранного JavaScript подтвердила, что в него не входят демонстрационные имена и meeting URL, а секретный API-ключ не попал в сборку.
- В живой базе проверено: обе таблицы включают RLS, строки доступа и расписания пока пусты, `anon` не имеет прав, `authenticated` имеет только ожидаемые операции.
- Живой вход с двумя пользователями, реальный deploy и доступ из сети второго пользователя ещё не проверены.
